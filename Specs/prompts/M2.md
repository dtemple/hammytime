## Hard dependency on M1 — resolve these before planning

M2 cannot be fully specified in the abstract because each of these is determined by an M1 implementation choice. For each, the M1.5 file proposed a seam; verify what M1 did and adjust.

1. **Tool → athlete side-effect channel (blocking).** `propose_day_override` and `propose_memory_update` are not like M1's tools: they must (a) write a `pending_proposals` row and (b) cause an inline-keyboard message to be sent to the athlete. How M2 does this depends entirely on M1's `runAgent` return contract:
   - If M1 took **M1.5 #1** (a `pendingActions: PendingAgentAction[]` field on the result), M2 adds variants to that union and a rendering switch at the call sites. Clean.
   - If M1 returns a bare string, M2 must **first** refactor `runAgent` to return structured output (do this as M2 step 0, it's a prerequisite), then proceed.
   - If the confirmed Agent SDK has a native "client tool" / side-effect concept, prefer it.
   Decide the proposal-emission design in preamble step 3 and get sign-off — everything else in M2 hangs off it.

2. **Where the plan is loaded (blocking for the effective-view work).** M2 replaces `plan_json` with `plan_json + active overrides` everywhere the plan is read. If M1 took **M1.5 #2** (single `loadActivePlan`), M2 wraps it once with `computeEffectivePlan`. If M1 left two readers (the `get_current_plan` tool and the daily pre-load), M2 must consolidate them first or update both. Confirm which.

3. **`agent_runs.kind` taxonomy (blocking for the re-run).** The "Already done" re-run records a row. If M1 took **M1.5 #4 / option (a)** and a `manual_completion`-aligned value exists, use it. If M1 took option (b) (four legacy values), M2 needs a constraint migration to add the value before the re-run path can persist honestly. Confirm and, if needed, make the constraint migration M2 step 1.

4. **Callable `manual_completion` path (blocking for §4.2 Layer 2).** The "Already done" button calls `runAgent({source:'manual_completion', chatId})` from a **callback handler** with no `messageText`. Verify M1's runtime doesn't assume a message is present (M1.5 #6). If it does, fix that assumption before wiring the button.

5. **Callback-data namespace.** Confirm onboarding still owns `injury:`-style prefixes and that the post-onboarding drop site (`bot.ts` ~388–402) is free for M2's `prop:` prefix. Telegram `callback_data` is 64 bytes — that's why proposals are referenced by short id, not inline payload (§4.6).

6. **Advisory lock (non-blocking but flag).** SPEC §3.7/§5.8 calls for a per-athlete `pg_advisory_xact_lock`. If M1 didn't implement it, note that M2's override writes + concurrent daily run are a (low-probability at single-athlete scale) write-conflict surface, and decide whether M2 adds the lock or defers it explicitly.

If items 1–4 can't be answered from the as-built M1 code, that's the signal to stop and pair on it rather than guess.

## Deliverable (what M2 actually ships)

Per `CONVERSATIONAL_COACH.md` §4.4, §4.5, §4.6, and §4.2 Layer 2.

### Migrations

- **`supabase/migrations/<ts>_plan_day_overrides.sql`** — the table from `CONVERSATIONAL_COACH.md` §4.5 verbatim (columns: `id`, `athlete_id`, `plan_version_id`, `override_type` check-constrained to the seven types, `target_date`, `payload jsonb`, `reason`, `proposed_by` check `('agent','athlete','manual')`, `confirmed_at`, `superseded_at`, `created_at`). Both partial indexes (`(athlete_id, target_date) where superseded_at is null` and `(athlete_id, plan_version_id) where superseded_at is null`). **Enable RLS** (match the initial-schema convention — every athlete-scoped table has RLS on, policies deferred). Add the table to the RLS TODO comment block.
- **`supabase/migrations/<ts>_pending_proposals.sql`** — the table from §4.6 (`id text primary key` short id, `athlete_id`, `proposal_type` check `('override','memory_update','activity_completion')`, `payload jsonb`, `created_at`, `expires_at default now()+24h`, `resolved_at`, `resolution` check `('confirmed','modified','cancelled','expired')` nullable). Enable RLS. Index `(athlete_id) where resolved_at is null`.
- **`agent_runs.kind`** — only if M1 didn't already reserve a `manual_completion`-aligned value (see dependency #3).

### Effective plan view

- **`src/server/agent/plan.ts`** (or wherever M1 left `loadActivePlan`) — add `computeEffectivePlan(planJson, overrides): Plan`. Pure function. Applies active (`superseded_at is null`, `confirmed_at not null`) overrides on top of base `plan_json` in a deterministic order. Handles all seven `override_type`s:
  - `move` (source date → rest, target date → the moved workout), `swap`, `replace`, `cancel` (→ rest), `modify` (field-merge into the day), `add`, and `manual_completion_marker` (does **not** change the planned workout — it annotates the day; see "Already done" below).
  - Conflict rule: later `created_at` wins when two active overrides touch the same date. Document it in a comment and test it.
- **`loadEffectivePlan(athleteId)`** — loads base plan + active overrides, returns the merged `Plan` plus `planVersionId`/`startDate`. This becomes the single reader used by the calendar, the `get_current_plan` tool, and the daily pre-load (per M1.5 #2).

### Calendar feed reads the effective view

- **`src/app/api/calendar/[token]/route.ts`** — fetch active overrides for the athlete and pass the merged plan to `renderPlanIcs`. The render layer (`calendar-render.ts`) shouldn't need to know overrides exist — it renders whatever `Plan` it's handed. Keep `renderPlanIcs`'s signature stable; just feed it the effective plan. (TTL is already `PT1H`; Apple/Google refresh on their own cycle per §4.5.)

### `get_current_plan` tool returns the effective view

- The M1 tool that returned raw `plan_json` now returns the effective plan. One-line change if M1.5 #2 was followed.

### Proposal tools (require athlete confirmation)

- **`src/server/agent/tools/propose_day_override.ts`** — params `(override_type, target_date, payload, reason)`. On call: validate the payload shape per override type, mint a short proposal id, write a `pending_proposals` row (`proposal_type='override'`), and emit a `PendingAgentAction` so the runtime sends the athlete an inline-keyboard card: human-readable description + ✅ Confirm / ✏️ Modify / ❌ Cancel. Does **not** write `plan_day_overrides` yet — that happens on Confirm.
- **`src/server/agent/tools/propose_memory_update.ts`** — params `(filename, action, payload, reason)` for the confirmed-write set from §4.4 (`add_injury`, `update_athlete_profile_section`, `update_injury_log_entry`, `update_race_calendar`). Same pending-proposal + inline-keyboard pattern. Applied via the existing `upsertMemorySection` / `injuries` writes on Confirm.

Register both with the agent. Update `coach.system.md` with a short paragraph on **when** to propose vs. when to just answer in prose — the agent should propose a day override when the athlete describes a concrete schedule change (travel, a wrecked body part, a missed day), not for hypotheticals.

### Generalized inline-keyboard confirmation framework

- **`src/server/telegram/proposals.ts`** — the callback dispatcher for `prop:` callbacks, callable from `bot.ts`'s post-onboarding callback branch. Token format `prop:<proposal_id>:<choice>` where choice ∈ `confirm|modify|cancel` (§4.6, 64-byte safe). On callback:
  - Load the `pending_proposals` row. If missing or `expires_at < now()`: answer "This proposal expired. Want to bring it up again?" and let the next agent turn regenerate (§4.6).
  - **Confirm** → apply the action (insert `plan_day_overrides` with `confirmed_at=now()`, `proposed_by='agent'`; or apply the memory write), mark the proposal `resolved`/`confirmed`, edit the card to a confirmed state.
  - **Modify** → mark `modified`, re-invoke the agent with "athlete wants to modify <proposal>" context so it iterates (§4.5.5).
  - **Cancel** → mark `cancelled`, the proposal dies, no override created.
- **`bot.ts`** — in the dropped post-onboarding callback branch, route `prop:`-prefixed callbacks to `proposals.ts`. Leave onboarding's `injury:` routing untouched.

### "Already done" button (§4.2 Layer 2)

- Agent responses sent in a context where "today's training so far" was relevant (cron / first-half-of-day) get two inline buttons: ✅ **Already done** / 👍 **Got it**. (This rides the same `PendingAgentAction`/keyboard plumbing; "Got it" is a no-op dismiss.)
- **Already done** → server (a) re-fetches Strava once; (b) if still nothing, writes a `manual_completion_marker` override for today via the proposal-confirm path (`proposed_by='manual'`, auto-confirmed — no second confirmation needed, the tap *is* the confirmation); (c) re-runs `runAgent({source:'manual_completion'})`; (d) sends the updated response. The system prompt already (from M1) honors a logged activity; add an instruction to honor `manual_completion_marker` identically.

## Constraints (working agreement)

From `CLAUDE.md` §9, made explicit for M2:

- **Scope.** Build exactly the deliverable above. If you find yourself wanting: `web_search`/`web_fetch`/`lookup_race` tools (M3), a per-athlete cost cap (M3), conversation summarization (deferred), the Haiku router (deferred), plan **regeneration** / `propose_plan_regeneration` (post-launch), or a `/edit_today` manual override command (deferred per §11) — stop and ask.

- **Anti-goals from `CLAUDE.md` §5** still apply.

## Hard rules on copy

Every athlete-facing string M2 adds — proposal card text, the human-readable override descriptions, the expired-proposal message, the "Already done"/"Got it" buttons, confirm/cancel acknowledgements — follows `CLAUDE.md` §3. Must not read as AI-generated. No "Great question," no "genuinely/honestly/straightforward," no "That's not X. That's genuine Y." The override descriptions especially must read like a coach noting a change ("Moved Saturday's long run to Sunday, dropped Thursday strength to balance it"), not like a database diff.

## Tests

- `computeEffectivePlan` — one test per `override_type`, plus the same-date conflict rule, plus `manual_completion_marker` leaving the workout intact while annotating the day. This is the highest-value test surface in M2 — the effective view is what the athlete sees on their calendar and what the agent reasons over.
- Proposal lifecycle — create → confirm applies the override; create → cancel applies nothing; create → expire (past `expires_at`) → tap returns the expired message and writes nothing.
- `propose_day_override` / `propose_memory_update` tools — payload validation per type, short-id minting, `pending_proposals` row written, correct `PendingAgentAction` emitted (no real Telegram send in unit tests).
- Callback dispatcher — `prop:` tokens routed correctly; `injury:` tokens still reach onboarding; unknown/foreign-athlete callbacks dropped safely (mirror the existing `answerCallbackQuery` guard).
- Calendar feed — renders an override (e.g. a moved long run shows on the new date and the old date is rest).
- "Already done" — synthetic context with no Strava activity → tap → `manual_completion_marker` written → re-run produces a response that references completed training, not a fresh prescription. This is the §4.2 trust test, Layer 2.
- Carry all M1-era tests forward green. Don't break onboarding, wellness, Strava, signup, or the M1 agent tests.

## Manual verification (Telegram, after CI passes)

`npm run dev:all`, then:

1. Chat: "I'm traveling Saturday, can we move the long run?" → agent proposes a move with a Confirm/Modify/Cancel card. Tap **Confirm**. Re-open the `/calendar` ICS (or re-fetch the feed) → the long run is on the new day, the old day is rest.
2. Same flow, tap **Cancel** → nothing changes in the calendar; the card updates to a cancelled state.
3. Same flow, tap **Modify** → agent re-engages and iterates on the proposal.
4. Mention a new injury ("my left achilles is acting up") → agent emits a `propose_memory_update` card. Confirm → `injury_log.md` / `injuries` reflects it.
5. Let a proposal sit past its TTL (or hand-edit `expires_at`), then tap a button → expired message, no write.
6. Morning cron fires with no Strava activity logged → message arrives with **Already done** / **Got it** buttons. Tap **Already done** → a `manual_completion_marker` is written for today and the agent's follow-up references completed training.
