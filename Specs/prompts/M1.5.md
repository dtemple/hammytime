# Prompt M1.5 — seam hardening between M1 and M2

This is a small companion to `Specs/prompts/M1.md`. It is **not** a separate Claude Code session. Fold these items into the M1 plan before you start writing M1 code — they are cheap to do during M1 and expensive to retrofit in M2.

## Why this exists

M1.md already asks the implementing session to surface its own improvements (preamble step 2). That review is from inside M1's scope. This file is the complementary view from inside **M2's** scope: it names the specific places where an M1 decision that looks fine in isolation forces a refactor of M1 code once M2 (day overrides + proposal/confirmation framework + "Already done" button) lands.

Everything here stays within M1's stated deliverable. None of it asks M1 to build M2 features. It asks M1 to leave clean seams where M2 will cut.

The ranking is by M2-rework-cost, highest first.

---

## 1. `runAgent` must return structured side effects, not just final text

**The seam.** M1's `runAgent` returns `{ finalText, runId, inputTokens, outputTokens, turnCount }` and the caller sends `finalText` to Telegram. Every M1 tool is read or direct-write — it returns data *to the agent* and produces no athlete-facing output of its own. So a string return is enough for M1.

M2 breaks that assumption. `propose_day_override` and `propose_memory_update` don't return data to the agent and finish — they have to cause an **inline-keyboard message** to be sent to the athlete (Confirm / Modify / Cancel) and a `pending_proposals` row to be written. If M1 hard-codes "runAgent returns a string; the caller calls `sendAndLog(finalText)`," then M2 has to either (a) re-architect the return contract, touching every call site (`bot.ts` ad-hoc path, cron route, the future manual-completion path), or (b) let proposal tools fire Telegram sends as hidden side effects from inside the tool body, which scatters send logic across tool files and makes ordering ("send the coaching text, *then* the proposal card") non-deterministic.

**The cheap M1 move.** Have `runAgent` return a result object that already has a place to carry post-run side effects, even though M1 populates none of them:

```ts
export type AgentResult = {
  finalText: string;
  runId: string;
  inputTokens: number;
  outputTokens: number;
  turnCount: number;
  // Reserved for M2. M1 always returns []. The caller is responsible for
  // rendering these AFTER finalText is sent.
  pendingActions: PendingAgentAction[];
};

// M1 ships this as an empty union / placeholder type. M2 fills it in.
export type PendingAgentAction = never;
```

Then the M1 call sites send `finalText` and iterate `pendingActions` (a no-op loop in M1). M2 adds variants to `PendingAgentAction` and the rendering switch without touching the contract or the call sites. This is ~10 lines in M1 and saves a cross-file refactor in M2.

If the Agent SDK you confirm in M1 step 2 has its own first-class notion of "tool produces a client-side effect" (some SDKs expose tool results plus a separate channel), prefer that and note it here so M2 builds on the SDK's grain instead of this hand-rolled field.

## 2. Single source of truth for "load the active plan"

**The seam.** M1 ships `get_current_plan()` returning the raw `plan_version.plan_json`, and M1.md is explicit: "Don't pre-bake an overrides-merged abstraction; that's M2." Correct call. But M1 *also* needs the planned-workout-for-today inside the user-message pre-load (today's `formatDayForPrompt` path in `daily-checkin.ts`). That's **two** readers of the plan.

M2's whole job for the calendar + daily read is to swap `plan_json` for `effectivePlan = plan_json + active overrides`. If M1 reads the plan in two places with two code paths, M2 has to find and wrap both, and risks one drifting (calendar shows overrides, daily read doesn't, or vice versa — exactly the kind of inconsistency §4.5 is trying to kill).

**The cheap M1 move.** Funnel both readers through one function — e.g. `loadActivePlan(athleteId): { planJson, planVersionId, startDate } | null` — and have `get_current_plan()` and the pre-load both call it. M2 then introduces `computeEffectivePlan()` in exactly one place and every reader inherits overrides for free. `daily-checkin.ts` already has `loadActivePlan` and `extractPlannedDay`; if M1 deletes that file, move them somewhere durable (M1.md already floats `src/server/agent/persistence.ts` — a `plan.ts` sibling is the natural home) rather than inlining them into the runtime.

## 3. Extract the timezone/date helpers M2 needs for override matching

**The seam.** `daily-checkin.ts` has `todayDateStr(tz)`, `todayDayOfWeek(tz)`, and `computePlanWeek(startDate)` as private functions. M1 may delete or gut that file.

M2 keys every override on `target_date` in **athlete-local** time and matches "is there an active override for today?" against exactly the same date the pre-load block prints in `## Today's training so far (athlete-local date YYYY-MM-DD)`. If those two date computations come from different code, you get off-by-one bugs at the timezone boundary that are miserable to debug and erode the §4.2 trust guarantee directly.

**The cheap M1 move.** Pull `todayDateStr`, `todayDayOfWeek`, `computePlanWeek` into a shared `src/server/agent/dates.ts` (or `src/lib/`), unit-tested, and have both the M1 pre-load block and (later) M2's override matcher import them. M1 is already touching this code; relocating three pure functions is nearly free and gives M2 a tested primitive.

## 4. Reserve the `agent_runs.kind` taxonomy for more than two sources — reconsider option (b)

**The seam.** M1.md offers two ways to fix the broken `agent_runs.kind` CHECK constraint and recommends option (b): reuse the existing four values, mapping `cron → 'daily'` and `ad_hoc → 'adhoc'`, dropping `'daily_checkin'`.

That's clean for M1's two sources. But M1's own `runAgent` signature already reserves a **third** source — `'manual_completion'` (the §4.2 Layer 2 "Already done" re-run, which is M2). M3 adds proactive/weekly synthesis runs. Under option (b), the manual-completion re-run has no honest home: it'd masquerade as `'adhoc'`, and you lose the ability to query "how often is Strava lag forcing a manual re-run?" — which is a real dogfooding signal §6 cares about.

**The recommendation.** Take **option (a)** instead, and make the value set mirror the `runAgent` `source` enum 1:1 so the mapping is identity, not a lookup table:

```sql
check (kind in ('daily','adhoc','weekly','plan_validate',
                'agent_cron','agent_ad_hoc','agent_manual_completion'))
```

or, cleaner, migrate to a source-aligned set (`'cron'`, `'ad_hoc'`, `'manual_completion'`, `'weekly'`, `'plan_validate'`) and backfill. Either way the point is: **decide the taxonomy in M1's migration so M2 doesn't ship a second constraint migration two weeks later.** If you keep option (b), at minimum write the constraint migration so M2 can `ALTER` it without a table rewrite, and leave a comment naming `manual_completion` as the known-incoming value.

This is the one place I'd actively push back on M1.md's stated recommendation.

## 5. Leave a clean post-onboarding callback-routing seam in `bot.ts`

**The seam.** Today `bot.ts`'s `callback_query:data` handler routes to onboarding only while `stepIdx < onboardingSteps.length`; **post-onboarding callbacks are answered and dropped** (lines ~388–402). M1.md correctly forbids building the M2 callback framework. But M1 *is* editing `bot.ts` (ad-hoc text routing), and the post-onboarding `handleInboundText` branch is right next door.

M2 adds a `pending_proposals` callback handler that must fire exactly in that dropped-callback branch. If M1 leaves the drop as an opaque `answerCallbackQuery(); return;`, M2 slots in fine — but it's worth a one-line comment marking it as the M2 insertion point so M2 doesn't have to re-derive the control flow.

**The cheap M1 move.** No code, just a `// M2: post-onboarding proposal callbacks route here` comment at the drop site, and **reserve a callback-data namespace** so M2's tokens can't collide with onboarding's. Onboarding uses bare prefixes (`injury:toggle:…`, `injury:done`). M2's spec format is `<action>:<proposal_id>:<choice>` (§4.6). Note in the comment that M2 will use a reserved prefix (suggest `prop:`) and that onboarding's namespace is `injury:`/step-scoped — so a dispatcher can branch on prefix cleanly. Keeping callback_data inside Telegram's 64-byte limit is on M2, but flagging the constraint here costs nothing.

## 6. Confirm the `manual_completion` re-run path can actually be invoked

**The seam.** M1.md says `runAgent` accepts `source: 'manual_completion'` as a reserved enum value "so M2 doesn't have to rename the contract." Good. But reserving the *enum value* isn't the same as the path being *invocable*. M2's "Already done" button needs to: re-fetch Strava once, write a `manual_completion_marker` override, then call `runAgent(..., {source:'manual_completion', chatId})` and send the result — from a **callback handler**, not the cron or the text handler.

**The cheap M1 move.** Make sure `runAgent` doesn't assume its trigger came from a `message:text` context (e.g. don't read `messageText` unconditionally, don't pull anything off a grammy `Context` that a callback handler won't have). M1 should be able to call `runAgent({source:'manual_completion'})` with no `messageText` and have it behave like a fresh coaching read. If M1 writes it so the only entry points are "cron" and "ad-hoc with a message," M2 inherits a runtime that quietly depends on a message being present. One M1 unit test — `runAgent` with `source:'manual_completion'` and no `messageText` produces a coaching read — locks this down.

## 7. Persist enough per-run trace for M2's proposal audit

**The seam.** M2 introduces athlete-confirmable actions (overrides, confirmed memory writes). When David is shadow-bcc'ing a new athlete and sees a weird override proposal, he'll want to know *what the agent was reasoning over* when it proposed it. That trace lives in `agent_run_steps` (already in the schema, `kind in ('tool','llm')`).

**The cheap M1 move.** M1 already persists `agent_runs`. While you're in there, persist `agent_run_steps` for each tool call and LLM turn (the SDK should expose the turn/tool sequence). M1.md lists this only implicitly. If M1 skips step-level persistence, M2's proposals will be auditable only by their outcome, not their rationale — and adding step capture later means re-instrumenting the runtime loop. Capturing it from day one is a few lines inside the tool dispatch M1 is already writing.

## What NOT to do in M1.5

To be explicit, none of the above licenses building: `plan_day_overrides`, `pending_proposals`, `computeEffectivePlan`, `propose_*` tools, the inline-keyboard confirmation framework, or the "Already done" button. Those are M2. M1.5 is only: return-shape reservation (#1), single plan loader (#2), shared date helpers (#3), the kind-taxonomy decision (#4), a routing comment + namespace reservation (#5), a callable manual-completion path (#6), and step-level trace persistence (#7). If any of these starts to balloon past "a seam," stop — it's leaking into M2.
