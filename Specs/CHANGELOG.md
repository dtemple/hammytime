- **v0.7.54 (2026-06-26) — Target-time pace fix: the pace→finish arithmetic moved from the model into code, activating the already-built-but-unwired `paceToFinish`. Web-only — `commit → push` (Vercel auto-deploys); NO migration, NO `fly deploy`. (`Specs/ONBOARDING_V3.md` §5.1, `Specs/TARGET_TIME_PACE_FIX_PROMPT.md`; closes the open `target_time` defect from the v0.7.53 V4-W6 run.)**
  - **The bug (surfaced by the `messy-time-goal` eval fixture).** When an athlete states a *pace* ("the Metro Marathon at 10-minute miles") the model did the pace→finish math itself and could store a wrong-but-in-band `target_time` — 10:00/mi for a marathon stored as 7:16:40 (26,200s) instead of 4:22 (15,720s). The model's prose got it right; the structured `target_time` in the tool call drifted. The deterministic backstop can't catch it (the marathon band is 2:00–7:30 on purpose, so 7:16 reads as plausible), and the recap echoed the model's prose rather than the stored slot — so the confirm never saw the divergence. The plan would have been built off paces ~3 hours slow.
  - **The fix — model parses, code does the math (the `goal_distance_mi` → `deriveBucketFromMiles` pattern).** A new `goal_pace_sec_per_mi` extractor field: the model emits the stated pace as seconds/mile (the one-step conversion it does reliably) and no longer computes the finish. The router validates the pace against `PACE_ENVELOPE_SEC_PER_MI` (230–1500 s/mi; out of range → re-ask) and computes `target_time = paceToFinish(pace, distance)` — against the real pocketed miles when there's a pocket, the bucket nominal otherwise — storing it `stated`. A pace stated before the distance lands is stashed on `V3OnboardingState.goal_pace_sec_per_mi` (JSONB, no migration) and applied when the race/distance arrives. The stated-finish-time path ("sub-4", "around 3:55" → `target_time` direct) and the "4:25" hours-vs-minutes ambiguity path are untouched.
  - **Confirm the stored value, not model prose.** When the pace block owns the turn it issues a `pending_confirm` on `target_time` echoing the code-rendered finish ("10:00/mi works out to about 4:22:00 for the marathon — that the goal?"), so the athlete validates the actual stored value — the check that would have caught 7:16.
  - **Recap belt-and-suspenders.** The deterministic recap's goal-time line now appends the implied pace (`• Goal time: 4:22:00 (~10:00/mi)`), derived from the REAL distance behind a pocket/adventure (not the bucket nominal), so a misread finish is visible against the pace the athlete actually stated. Empty for keep_fit or when no distance resolves.
  - **The same-turn race-lookup case (decision, flagged to David).** The real `messy-time-goal` shape fires the race lookup AND the pace on one turn, and the race confirm ("Found it — … That the one?") owns that turn's message. Rather than stack a second confirm, the pace-derived finish is stored **silently** there and the recap is the net — it renders the `Goal time` line from the same stored slot, so display and storage now agree everywhere (the actual root cause; the old bug was display ≠ storage). The dedicated pace-confirm fires only when no higher-priority thread (race confirm / pending pocket consent / off-ramp / backstop) owns the turn.
  - **Verified.** Full suite **1235 green** (+6 router tests: compute+confirm, out-of-envelope re-ask, stash, stash-apply, same-turn-race-lookup silent store, real-pocket-miles; +2 recap-pace tests), typecheck, lint, build clean. The V4-W6 `messy-time-goal` eval (real Sonnet, ~$1.6) was **not** re-run this session (David's call) — the unit tests cover the mechanism deterministically; re-run `npm run eval` to confirm the end-to-end Sonnet behavior before the launch gate.

- **v0.7.45 (2026-06-24) — cap `checkin_log.md` read-path tokens with worker-owned log rotation at hydrate.   - **Why (cost only).** The plan is ~14k tokens (already compacted) and is loaded in 76% of coaching runs, often more than once — and `cache_creation` is ~54% of total spend, so re-loading the whole plan every routine run is the largest cost lever left untouched after json-compact. This is purely a read-path efficiency change: the daily/ad-hoc coaching message rarely needs the entire season in context, only the days around now.
  - **Not a correctness or edit change — that ground is already covered.** An earlier draft of this entry also proposed a structured plan-edit tool (a "Plan Access Layer") to stop silently-dropped invalid edits. That is now **redundant and dropped**: the edit path was hardened in the meantime — `worker/plan-edit-hook.ts` re-validates the plan in-loop after every Write/Edit and blocks a broken candidate with the schema issues as feedback; `worker/plan-repair.ts` does a one-shot fix; `persistPlanEdit` stages a **proposal** (`propose_plan_edit`) the athlete confirms with a tap, and alerts David on a drop. The remaining edit-cost saving (~$1.5/wk of output tokens on ~14 edits/wk) no longer justifies reopening the §4 tool-lock and coexisting with that machinery. So this entry is read-only; **the edit/hook/proposal path is left entirely alone.**
  - **What it is — a derived view, the same pattern as `plan_drift.md`.** At hydrate, the worker writes one extra read-only file (`plan_view_readonly.json`, built by `worker/plan-current-block.ts`, serialized with `compactJson`) alongside the full plan, holding: **full day-level detail for the current week + next 2 weeks** (`ACTING_WINDOW_WEEKS = 3`), a **one-line-per-week skeleton of the remaining future weeks** (week number, phase, planned weekly miles, start/end dates, any `coaching_note`), the plan **`metadata`, `agent_guidance`, and `strength_workouts` kept whole** (strength session content is referenced by the near-term full-detail weeks), and past weeks **collapsed hard** (see below). The coach reads this for routine work instead of the full ~14k plan.
  - **Weight the detail toward the future.** The future matters more than the past, so the view is asymmetric, not a symmetric window. Past completed weeks collapse to a single rolled-up summary line (phase span + average planned miles), keeping at most the immediately-preceding week as a skeleton line for continuity — because the coach gets actuals from `strava_recent.json` (last 14 days) and plan movement from `plan_drift.md`, so the *prescribed* detail of an old week is redundant. The current week (where reconciliation happens) is already in the full-detail window. The budget the past frees up is spent forward: the acting window, the always-on races list, and near-race lead-ins. A genuine look-back is one Read of the full plan away — the same escape hatch as a forward-looking question.
  - **Minimizing context loss (the load-bearing part).** The skeleton keeps the whole arc in view at a few hundred tokens, so the coach still knows where today sits — peak week, when the taper starts, how the build is shaped — and knows when it needs more. `coach.md` instructs it to **open the full `marathon_training_plan.json` for any whole-arc / forward-looking question and for every edit.** Far-week day-level detail is the only thing not in the default view, and it's one Read away. Keeping `metadata` + `agent_guidance` whole means pace zones, compliance rules, and race facts are never dropped.
  - **Tune-up races must never fall into the skeleton.** A tune-up race is a `type: "race"` day inside `weeks[].days[]` (the goal race is `metadata.race`); they also arrive from onboarding's `tuneup_races`. One several weeks out would otherwise show only as a skeleton line and the coach would miss it — so the view **always surfaces every race day across the whole plan** (date, distance/description, week number, phase) plus the non-placeholder goal race (`isPlaceholderRace` suppresses the synthetic one), regardless of the current-block window. The week containing a race and the **2 weeks before it** (`LEAD_IN_WEEKS`) are pulled in at full day-level detail when the race is within the **6-week near horizon** (`NEAR_HORIZON_DAYS = 42`), so the lead-in is visible without a Read. `coach.md` directs the coach to build a taper into an upcoming tune-up — even a small one — and to open the full plan to shape it. The races-visible guarantee is explicit, not a side effect of where the window happens to fall.
  - **What changes.** `folder.ts` hydrate writes the view (reusing `compactJson`) and adds it to `INPUT_ONLY_FILES` so it's never synced back — exactly how `plan_drift.md` is handled. `coach.md`'s "The files" gains the view and a read-routing instruction (view for routine, full plan for arc + edits). Everything else is untouched: the edit path (`Edit` on the full file → `plan-edit-hook` → `persistPlanEdit` proposal), the DB's monolithic JSONB, and the calendar/plan-drift/onboarding consumers.
  - **The tradeoff, stated honestly.** Routine runs load much less; edit and whole-arc runs load the view *and* then the full plan (slightly more than today). Net positive because routine non-editing runs dominate the volume. It is a behavior change to what the coach sees by default, so it needs watching on real transcripts (any rise in "I don't have that in front of me" or thinner long-range coaching) — and it's trivially reversible (stop writing the view, point the coach back at the full file).
  - **Measured.** On the seed plan (22 weeks), the view serialized to **4.4k tokens vs the full plan's 12.4k — a 64% cut** on the routine read. Live before/after via `scripts/plan-token-audit.ts <deploy-timestamp>` on non-editing-run `cache_creation`; expected ~$3–5/wk off, scaling with athlete count.
  - **Verified.** New `plan-current-block` suite (window selection across plan boundaries; past collapse incl. the kept skeleton tail; races always surfaced incl. a far tune-up; placeholder-race exclusion; near-race lead-in expansion; serialization; real seed) + `folder.test` additions (view written when the plan is valid / skipped when invalid / never synced back). 1153 tests, typecheck, lint, build green. `hydrate` now takes the athlete timezone to place today's window.
  - **Context-loss watch (the part a unit test can't prove).** Watch live transcripts for thinner long-range coaching, missed tune-up tapers, or "I don't have that in front of me." Trivially reversible: stop writing the view + revert the `coach.md` routing bullet.

- **v0.7 (2026-05-28) — agent runtime moves to a worker container (the big one).**
  - **Why:** the Claude Agent SDK can't run inside a Vercel serverless function. The SDK spawns a native `claude` binary as a subprocess; the linux-x64 binary is ~240 MB uncompressed and Vercel's per-function uncompressed limit is 250 MB (not configurable, enforced by AWS). There's no room for the binary plus the Next.js runtime and deps. This is not a packaging bug — both Anthropic's hosting guide and Vercel's own KB document that the Agent SDK is a **long-running process meant to run in a container**, not a function.
  - **What changes:** the agent runtime moves from "Agent SDK in a Vercel serverless function" to "**Agent SDK with its built-in tools, running in a Fly.io worker container, one working directory per athlete**." This is a near-1:1 port of the personal coach in `~/projects/health-agent`: a folder of markdown/JSON files + Claude Code's built-in Read/Write/Edit/Glob/Grep/Bash/WebSearch tools + a `CLAUDE.md`-style system prompt + a Strava-fetch script. The agent improvises with general-purpose tools instead of relying on a fixed set of hand-written custom tools — which is the capability that makes the local experience good.
  - **What this deletes vs. the prior plan:** no custom in-process MCP tool catalog, no `memory-io` read/write layer, no hand-rolled agent loop. Built-in tools replace all of it. The single-shot `agent/daily-checkin.ts` LLM call is also retired.
  - **Decisions locked (2026-05-28):**
    - **File storage:** `memory_files` table stays the durable source of truth. Each run hydrates the athlete's folder from `memory_files` to the worker's disk, the agent reads/writes files freely, then changed files sync back to `memory_files`. No new storage product; reuses the `import-memory-files` script.
    - **Scheduling:** the Vercel cron stays but only _enqueues_ daily jobs into `job_queue`. The worker drains `job_queue` (with `FOR UPDATE SKIP LOCKED`) for both daily and ad-hoc runs — one execution path.
    - **Host:** Fly.io. Cheap always-on machines, first-class persistent volumes, and a clean path from one machine to a worker pool behind the queue as athlete count grows.
    - **Billing at $0:** finish the in-flight run (don't cut off mid-reply), then block new runs with a top-up message until the athlete reloads credit.
    - **Isolation:** per-athlete `cwd`; Bash restricted to the athlete's folder plus the Strava-fetch script; deny-by-default on anything network/destructive. Multi-tenant isolation (one athlete's agent must never read another's folder) is the real new engineering — it replaces "endless edge-case custom tools."
  - **Revenue model (new):** free for the first ~20 friends, then **prepaid pay-per-usage** — an athlete pre-loads credit (e.g. $10) that draws down by agent usage. This makes per-run token/cost metering a first-class feature. `agent_runs` becomes the billing ledger; a new `athlete_credits` balance is decremented per run. Payments move from "out of scope" (v0.3) to **in scope from ~20 users**.
  - **Vercel keeps:** the web app (signup, Strava OAuth handoff, plan view, admin), the Telegram webhook receiver, and the cron _enqueuer_. Only agent _execution_ leaves Vercel.
