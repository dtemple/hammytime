### New code

- **`src/server/agent/agent-runtime.ts`** — exports `runAgent(athleteId, opts)`. `opts` includes:
  - `source: 'cron' | 'ad_hoc' | 'manual_completion'` (the third is a placeholder enum value; the M2 button isn't wired this prompt — but the runtime accepts the value so M2 doesn't have to rename the contract).
  - `messageText?: string` — the inbound athlete message for `ad_hoc`; omitted for `cron`.
  - `chatId: number | string` — used by the typing wrapper.
  - Returns `{ finalText: string; runId: string; inputTokens: number; outputTokens: number; turnCount: number }`.
  - Bounded by `max_turns` (start at 6 — surface as a constant at top of file).
  - Wraps the Agent SDK session. System prompt loaded from `src/server/agent/prompts/coach.system.md`. Tools registered per the catalog below.
  - On error: log to Sentry, persist an `agent_runs` row with the error string, send the athlete the soft fallback from `Specs/CONVERSATIONAL_COACH.md` §12 ("Hit a snag — try again? If it keeps happening, ping David."), re-throw so the caller can decide what to do.

- **`src/server/agent/prompts/coach.system.md`** — extracted from `~/projects/health-agent/CLAUDE.md`, parameterized with placeholders the runtime fills at invocation time (`{{athlete_name}}`, `{{goal_race}}`, `{{key_injury_history}}`, `{{plan_week_n}}`, `{{plan_day_of_week}}`, `{{today_iso}}`, `{{today_strava_block}}`). Reviewable as a standalone artifact — if reading it doesn't feel like reading a coaching brief, the extraction missed something (`CONVERSATIONAL_COACH.md` §12).
  - Must contain the mandatory-activity-awareness paragraph from `CONVERSATIONAL_COACH.md` §4.2 verbatim — the one about checking `## Today's training so far` first.
  - Must contain the date-of-record rule and prehab rules from the existing `src/server/agent/prompts/daily-checkin.system.md` (those carry over; don't lose them in the extraction).
  - Must NOT instruct the agent to use HR zones, open with sycophancy, or write more than ~400 words in the daily check-in path. Same hard rules as today.

- **`src/server/agent/tools/`** — one file per tool, each one a small TS module exporting a tool definition the Agent SDK can register. Tool catalog for M1 (per `CONVERSATIONAL_COACH.md` §4.7, M1 subset):
  - **Read tools**
    - `read_memory_file(filename)` — returns content_md for the named file for the current athlete.
    - `list_memory_files()` — returns the list of `(filename, last_updated)` tuples that exist for the athlete.
    - `fetch_strava_activities(start_date, end_date)` — wraps `fetchRecentActivities`. Bounded range (max 90 days). Returns the same `StravaActivitySummary[]` shape today's runtime uses.
    - `get_current_plan()` — returns the active `plan_version.plan_json`. In M1 there are no overrides yet, so "effective plan" == `plan_json`. Don't pre-bake an "overrides merged in" abstraction; that's M2.
  - **Direct-write memory tools (no athlete confirmation)**
    - `append_to_memory_file(filename, entry)` — wraps the existing `appendCheckinEntry`-style raw-append pattern. Accepts any log-shaped file (`checkin_log.md`, `wellness_log.md`, `open_questions.md` log section, etc.). Server enforces: only allowlisted filenames, max entry size 8 KB.
    - `update_memory_file_section(filename, section_name, content)` — wraps the existing `upsertMemorySection`. Server enforces: only allowlisted filenames.
    - `add_open_question(text)` — adds a row to the open_questions.md table-shaped section.
    - `mark_open_question_resolved(id, resolution)` — closes an open question by id.

  Tools the agent does NOT have in M1 (M2 territory; explicit anti-goal for this prompt): `propose_day_override`, `propose_memory_update`, `web_search`, `web_fetch`, `lookup_race`. If you find yourself wanting one of these, that's a signal the deliverable has crept — stop and tell me.

### Pre-load the activity-awareness block

This is the single highest-trust feature in M1 (`CONVERSATIONAL_COACH.md` §4.2, §6). Implementation: before `runAgent` calls the SDK, fetch today's Strava activities for the athlete and append a block to the user message in the literal format from §4.2:

```
## Today's training so far (athlete-local date YYYY-MM-DD)

<if activities exist>:
- <type> · <distance_mi> mi · <duration_min> min · started <HH:MM local>
- <athlete title/notes if any>
<if no activities>:
Nothing logged on Strava today yet.
```

Server builds this deterministically. The system prompt (in `coach.system.md`) explicitly instructs the agent to read this section first. Tests must cover the "agent has activities, recommends a run anyway" failure mode — feed a synthetic context with a logged activity, assert the response references the activity rather than prescribing a fresh run. This is the kind of test that's worth writing carefully.

Note: this is Layer 1 of the §4.2 fix. Layer 2 (the "Already done" inline button) is M2 and out of scope here.
